## 本次核实纠正了什么

1. 此 tag 中 `examples/` 有 178 个直接子目录。这个数字不是“178 道标准题”，也不表示全部示例能在本机运行。
2. 此 tag 不存在 `doc/examples.html`、`doc/demos.html`。原 11 号文档不能按这两个路径提取“150+ 官方描述配对”。`examples/CMakeLists.txt` 是条件化构建目录清单，不是逐例的自然语言答案库。
3. `include/osg/Geode:28` 明确为 `Geode : public Group`，`include/osg/Group:51` 声明 `addChild(Node*)`；`src/osg/Geode.cpp:38-41` 中 `addDrawable` 直接调用 `addChild`。不得把二者机械标为正负例，更不能把 Geode::addChild 判为虚构。
4. `include/osg/Geode` 的注释仍称其为 leaf node；说明注释、继承结构和实现需要一起看，不能只摘一句话形成绝对结论。
5. OSG 多个公开头文件没有 `.h` 后缀，如 `include/osg/Geode`。只使用 `*.h` glob 会漏掉核心语料。按 manifest 文件清单读取。
6. `doc/Doxyfiles/all_Doxyfile` 存在，是模板配置，包含 CMake 路径变量，且默认 `GENERATE_XML = NO`。并非下载后就已经有完整 Doxygen XML/HTML；第一版无需依赖它。
7. 示例运行可能依赖模型、图片、字体、插件和构建选项。README 提及 OpenSceneGraph-Data、OSG_FILE_PATH 和 BUILD_OSG_EXAMPLES。当前只做源码检索，不承诺返回的示例无需依赖就能运行。

## 第一版做什么

目标：回答 OSG 3.6.5 的局部 API / 示例查询，返回中文解释和精确来源。

离线链路：
原始文件 → 清洗与切分 → chunk 元数据 → 文档向量 + 关键词索引。

在线链路：
用户问题 → query 向量/关键词检索 → 可选融合与重排 → 证据片段 → 生成中文回答及引用。

先完成读取、切分和检索，再接生成；最后把已有检索函数包成 MCP 工具。这样每一层都可单独检查。模型或框架不会自动修复缺失的原始证据。

建议顺序：

1. 运行 `./verify.ps1`，打开开发题 001 对照原文件，确认“问题—答案—证据”的关系。
2. 根据 manifest 的 indexable 字段读取文件；输出 chunk_id、source_path、start_line、end_line、version、text。保留原始行号，不要在去掉注释后重新编号。
3. 首版可使用固定窗口与重叠切分建立 baseline，再实验“注释+声明”切分。先理解可复现数据流，无需先做完整 C++ AST。
4. 独立跑 BM25 与 dense，检查十道题各自召回了什么；小样本结果只用于调试。
5. 两路以同一 chunk_id 去重，RRF 融合，再实验 reranker。FTS5 的 bm25() 越小越好，必须按正确方向排序。
6. 接生成，要求回答引用实际返回的片段；没有足够证据就说明不能确定。先看错误样本，再调提示词。
7. MCP 第一版暴露 search_docs 即可；之后做 API 清单，再加 get_api_ref。MCP 检索服务不自动控制客户端最终回答或整个 Agent 循环。

## 开发题如何使用

这些题已经参与资料选择，是开发集，不能用于宣称对真实用户的泛化效果。证据位置是已核实的支持性片段，不是穷尽相关性标注。

- “命中一个来源文件”只说明粗定位成功，不代表召回片段包含答案。
- 先查看返回 chunk 是否覆盖必要证据，再评价答案。
- 题 002 需要继承声明与实现等组合证据；检索到 Geode 类名本身不够。
- 改进前后固定语料、切分与候选数，逐次改变量。
- 以后另建冻结测试集，按问题家族划分，加入版本不匹配、歧义和库外题。
- 无法仅凭本次选取的 29 份文本断言“整个 OSG 不存在某 API”。
